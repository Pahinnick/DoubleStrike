# Handoff — DoubleStrike

Read this first if you're picking this project back up. It's a Vite + React + TypeScript single-page app: Scryfall search and deck building in one screen (no more tab-switching between Scryfall and a deck builder), with a pip-accurate "average turn castable" stat as the headline feature.

The original design plan (product rationale, architecture, math spec) lives outside this repo, in the local Claude plans folder as `hashed-singing-puffin.md` — read that for *why* things are shaped the way they are. This doc is about *current state* and *things that will bite you*.

## Status

All planned MVP work is done: 12 original build-order tasks + a follow-up "find similar cards by Scryfall tag" feature, plus a solo-playtest mode (battlefield/hand/zones, pan-and-zoom battlefield, tokens, counters, life/commander-damage/poison, a right-click context menu with flip/transform, a library tutor, and an Actions tray with scry/surveil/cascade) built out from the playtest backlog below. 184 tests passing, clean typecheck, no lint errors (5 harmless `react-refresh` warnings — see Known Quirks). Now a git repo (initialized 2026-08-02 at the user's request). No remote is configured yet — the project is intended to go public eventually, so keep tracked files free of the user's real name, email, and local machine paths.

## Running it

```
npm run dev      # or use the Claude_Preview MCP tool with .claude/launch.json's "dev" config
npm test         # vitest run
npx tsc -p tsconfig.app.json --noEmit   # typecheck (no `npm run build` — see quirk below)
npx eslint .
```

**`build.bat`** (project root) runs `npm run build` (`tsc -b && vite build`) for the user to run by hand — cd's to its own folder first (so it works regardless of where it's launched from), runs `npm install` automatically if `node_modules` is missing, and pauses at the end so a double-click doesn't just flash a window shut. Verified working live on this machine (Node v18.12.1) as of this session — despite the caution below about not routinely running `npm run build`, it does actually succeed here; that caution is about not defaulting to it for typecheck purposes (slower, and `tsc -b`'s incremental build info can mask/differ from a plain `--noEmit` run), not that the command is broken.

## Environment quirk that will trip you up

**Node is v18.12.1** on this machine, not the newer LTS you'd expect in 2026. Several tool versions are pinned *below* their `package.json`-declared latest specifically because of this:

- `vitest@1.6.0`, `jsdom@24`, `@testing-library/react@14`, `@testing-library/jest-dom@6` — the current majors of these require Node 20+/22+ and will hard-fail on this box. Don't blindly `npm update` these.
- `create-vite@5` was used for scaffolding (not `@latest`) for the same reason.
- If you ever see `npm WARN EBADENGINE`, that's expected noise from *other* transitive deps (eslint tooling etc.) that don't actually break at runtime — only vitest/jsdom actually failed outright when left at latest.

                            layouts by preferring card_faces[0] over the top-level field (see quirk below).

## Known quirks / traps discovered this session

1. **Scryfall split/adventure/flip cards lie about `mana_cost` at the top level.** For layout `split`/`adventure`, the top-level `mana_cost` is a *combined display string* like `"{1}{R} // {1}{U}"` — not a single parseable cost. `getCastingManaCost()` in `api/scryfall.ts` handles this by always preferring `card_faces[0].mana_cost` when `card_faces` exists, only falling back to top-level `mana_cost` for normal single-faced cards. If you ever see a mana-cost-dependent stat look wrong for a split/adventure/transform card, check this function first. Verified live against Fire // Ice, Brazen Borrower, Wear // Tear.

2. **React 18 StrictMode double-invokes effects in dev**, and this caused a real bug: `DeckListContext.tsx`'s bootstrap effect originally checked `if (cancelled)` *after* calling `saveDeck()`, so the discarded first StrictMode invocation still persisted an orphan empty deck to IndexedDB before bailing. Fixed by moving the cancellation check to right after the first `await`, before any write. If you add new async bootstrap-style effects, put the cancellation check before the first side-effecting call, not after.

3. **Scryfall has no per-card "what tags does this card have" API.** Tags (Oracle tags = functional, Art/illustration tags = visual) only exist as bulk data files updated daily, keyed the other way around (tag → list of oracle_ids). `storage/tagIndex.ts` downloads the Oracle Tags file once (~18MB JSON, not the smaller `.jsonl.gz` — gzip streaming was skipped for implementation simplicity, see file comments) and builds *both* directions in memory: `cardTags` (oracle_id → tags) and `tagCards` (tag → oracle_ids), so both "what are this card's tags" and "who else has this tag" are O(1)/cheap lookups afterward. `oracle_id` (not `id`) is the join key — confirmed live that `/cards/collection` accepts `{oracle_id}` as an identifier.

4. **The Claude_Preview browser console log tool returns stale entries across HMR reloads.** Twice this session, `preview_console_logs` showed alarming `DeckPanel`/`DeckCardRow` errors that turned out to be leftover log-buffer entries from an earlier, already-fixed code version (confirmed by fully stopping/restarting the preview server and re-checking — errors vanished). If you see a scary error after making edits, restart the preview server (`preview_stop` + `preview_start`) before trusting it's real.

5. **`getDisplayImage()` in `api/scryfall.ts` was widened to accept a minimal structural type** (`{ image_uris?, card_faces? }`) rather than a full `ScryfallCard`, specifically so `CardSnapshot` (storage) and `TaggableCard` (the similar-cards feature) can reuse it without duplicating the "prefer front face" logic. `cardCache.ts`'s `getSnapshotImage()` just delegates to it now. Keep reusing this rather than re-writing the front-face-fallback logic a third time.

6. **A "stuck on Loading profiles…/Loading your decks…" report (2026-07-15, from a user's friend) traced to a real bug: neither startup bootstrap effect had error handling.** `ProfileContext.tsx`'s and `DeckListContext.tsx`'s bootstrap `useEffect`s called their async setup with no `.catch()` — any failure (a thrown error from storage, a rejected IPC call, corrupted persisted data) left `ready`/`activeProfileId` permanently unset, so the app hung forever on a bare loading `<div>` with **zero error, zero retry, zero diagnostic info**. Whatever the friend's actual root cause was, this is why it looked like an infinite hang instead of a visible, actionable error. Fixed:
   - Both bootstrap effects now `.catch()` and store the error; a new shared `src/components/shared/BootstrapError.tsx` renders the message + raw error detail + a **Retry** button (bumps a `retryToken` state included in the effect's deps, re-running bootstrap without a full page reload) instead of the app hanging silently.
   - **Most likely concrete root cause on the desktop (Electron) build**, hardened defensively even though not confirmed against the friend's actual machine: `electron/storage.cjs`'s `readJson()` only handled `ENOENT` specially — a corrupted/truncated `app-data.json` (e.g. from a crash or power loss mid-write) threw a `SyntaxError` that propagated all the way up and (pre-fix) hung the renderer forever. Now `readJson()` catches `SyntaxError` specifically, **quarantines** the bad file by renaming it to `<file>.corrupted-<timestamp>` (never deletes — still hand-recoverable) rather than the app being unrecoverable, and falls back to reseeding a fresh default. Other fs errors (permissions, etc.) still propagate — now visibly, via the UI fix above, instead of hanging.
   - **Verified live**: temporarily forced `bootstrapProfiles()` to reject in the browser dev build, confirmed the new `BootstrapError` UI renders correctly with the real message, and confirmed clicking Retry fully recovers (deck loads normally) without a page reload — then reverted the temporary test code. Did **not** reproduce/verify the Electron-specific quarantine path live (would need an actual corrupted `app-data.json` in a packaged build) — sanity-checked by reading the code path only.
   - If this pattern shows up again in a *new* async bootstrap effect, don't repeat the mistake: always `.catch()` (or otherwise handle rejection) around anything gating a `ready` flag that blocks the whole app render.
   - **Round 2, same day, real data-loss report:** the fix above only quarantines *corrupted* JSON (a `SyntaxError`). The friend's actual `app-data.json` had been *renamed* per our own manual-workaround instructions — that's ENOENT, not a `SyntaxError`, so quarantine never ran; `loadAppData()` fell straight through to "profiles list is empty → silently reseed one blank profile," making his real profile/decks (never actually deleted, just orphaned on disk) look completely gone. **Fixed with an orphan-recovery scan** added to *both* storage backends:
     - `electron/storage.cjs`: `recoverOrphanedProfiles()` scans `profiles/` on disk for folders missing from the loaded profile list and re-registers them as `Recovered Profile N`.
     - `src/storage/indexedDbAdapter.ts`: mirrors this for the browser build — scans `decksStore` for `profileId::deckId` keys whose `profileId` isn't in the profile list, via a new exported pure helper `findOrphanedProfileIds()` (5 unit tests).
     - Both are **tombstone-safe**: `AppData.deletedProfileIds` (new field, `state/types.ts`) is written by `deleteProfile` in both adapters, and the recovery scan skips any id in it — so this can never resurrect a profile someone actually deleted (that's still intentional: `deleteProfile`'s comment about leaving decks on disk on purpose is unchanged).
     - **Verified live**: reproduced the friend's exact failure in the browser dev build — wiped just the `mtgdb:appData` IndexedDB entry via raw `indexedDB` calls (leaving the two real deck rows in `decksStore` untouched, confirmed via `getAllKeys()` first), reloaded, and confirmed a `Recovered Profile 1` appeared holding the original profile id with both decks intact and the deck view loading normally — read the persisted `mtgdb:appData` entry back afterward to confirm it matches. 273 tests pass, clean tsc/eslint.

7. **Multiplayer pod: an opponent's card that isn't in your own deck rendered as a grey placeholder showing the raw Scryfall UUID instead of art** (reported 2026-07-15, live two-deck pod play). Root cause: `useCardSnapshots.ts` only read the local snapshot cache and background-refreshed entries that were *stale* — it never fetched an id that was **missing from the cache entirely**, silently dropping it forever (`if (!snapshot) return`, no retry). Your own deck's cards always get cached on import/add, so this never showed up solo; an opponent's card you don't own a copy of has simply never been seen by your client, so it was permanently unresolved. `PlaytestCard.tsx`'s placeholder then fell back to `gameCard.scryfallId` (a raw UUID) as the display name when there was no snapshot — that's the "card code printed on it" the report described.
   - **Fixed**: `useCardSnapshots.ts` now also fetches ids missing from the cache (merged into the same `getCardsByIdentifiers` batch as stale refreshes, deduped by the same session-scoped `refreshedIds` set so it's not retried every render). The final cache-merge step changed from a guarded `if (next.has(card.id))` to an unconditional `.set()` — that guard was correct for stale-only refreshes (always pre-existing in the map) but would have silently dropped every newly-fetched missing id, since those never had an existing entry to gate on.
   - `getCardsByIdentifiers` (`api/scryfall.ts`) already batches/chunks by Scryfall's collection-endpoint limit and dedupes via its own in-memory cache, so no additional rate-limit handling was needed for a pod with many unseen opponent cards.
   - **Verified live**: temporarily injected a real, confirmed-uncached Scryfall id (Black Lotus) into the dev "Preview pod" mock-opponent battlefield, confirmed it rendered a placeholder-free real image (`cards.scryfall.io/.../bd8fa327-....jpg`) and that the snapshot was persisted to `mtgdb-card-snapshots` afterward (`name: "Black Lotus"`) — then reverted the temporary test code. 273 tests pass, clean tsc/eslint.

8. **The life bubble (both solo `LifeOverlay` and pod `SeatOverlay`) is now split into four click zones instead of left-click-+1/right-click--1** (2026-07-15, user request): top = +1, bottom = -1, left = -10, right = +10 — one click for both fine and coarse life changes. New shared `src/components/playtest/HealthBubble.tsx` renders four `position:absolute; inset:0` buttons clipped into N/S/E/W triangular wedges via `clip-path: polygon(...)` from center to each corner (a circle inscribed in a square, split by its two diagonals — clipped to the circle by the parent's `overflow: hidden`), plus a `pointer-events: none` centered value span so it doesn't block clicks to whatever wedge is beneath it. Wired into `LifeOverlay.tsx` (solo) and `SeatOverlay.tsx` (pod, **only for your own interactive bubble** — an opponent's read-only life mirror is unchanged, still the plain non-wedged `SeatBubble` span, since wedges make no sense on a value you can't edit). Poison and commander-damage bubbles are untouched (still the old click/right-click ±1 gesture) — only life got the 4-way split.
   - **Real regression caught during live verification, fixed at the CSS level:** `.playtest__life-bubble`'s border only ever declared `border-width: 2px` (no `border-style`) and relied entirely on a `<button>` element's implicit non-`none` default border-style from the UA stylesheet to actually render — invisible when it worked, because it always *had* been a `<button>`. Converting the wrapper to a plain `<div>` (now needed since it holds 4 separate buttons, not one) silently dropped the border to `0px` computed width with zero visual indication in a screenshot beyond "looks a little off." Caught by explicitly checking `getComputedStyle(...).borderWidth` in the browser console before trusting a screenshot. Fixed by adding an explicit `border-style: solid;` — `.playtest__seat-bubble` (pod) was already safe since it used the `border: 2px solid ...` shorthand from the start. **Lesson: a border/outline that "just worked" on a `<button>` and needs to move to a non-form element must have its border-style/outline made explicit, not assumed** — computed-style inspection catches this class of bug far more reliably than a screenshot.
   - **Verified live**: dispatched real clicks on each of the four wedges (both the solo bubble and the pod self-bubble) and confirmed each exact delta applied via the rendered value (40→41 top, →51 right, →50 bottom, →40 left — net zero, back to 40) and confirmed the opponent-mirror bubble still renders as a plain read-only `<span>` with zero wedges. 273 tests pass, clean tsc/eslint (no new component/hook test infra exists in this codebase to unit-test — matches the project's existing pure-logic-only testing boundary).

## Deck import — Archidekt (paste export **and** link)

`ImportDeckModal.tsx` imports two ways, both feeding one pipeline (`importParsed` — resolve via Scryfall's collection endpoint, `createDeck`, then dispatch cards/categories/commander/board):

- **Plain-text export** (original): pasted into the textarea, parsed by `parseArchidektExport` in `engine/deckImport.ts`.
- **Deck link** (new): paste an Archidekt URL → `parseArchidektDeckId` pulls the numeric id → fetch `archidekt.com/api/decks/{id}/` → `parseArchidektDeckJson` maps it to the same `ParsedDeckCard[]`. The deck name is taken from Archidekt when the user leaves the name field at its "Imported Deck" default. Cards in any Archidekt category flagged `includedInDeck: false` (built-in "Maybeboard" and custom exclusion categories) go to the **sideboard**; a card's functional `category` is the first tag that's neither "Commander" nor an excluded one. Partner commanders work (both get `isCommander`). Verified live end-to-end against a real 140-entry partner deck.

**The CORS split (important):** Archidekt's API sends no permissive CORS headers, so the renderer can't fetch it directly. `src/api/archidekt.ts` picks the transport at runtime:
- **Packaged/Electron app:** main-process fetch over a new IPC channel — `electron/net.cjs` (`net:fetchArchidektDeck`), registered in `main.cjs`, exposed as `window.electronNet.fetchArchidektDeck` in `preload.cjs`. Node's global `fetch` (Electron 32 → Node 20) isn't subject to CORS. **This path is built following the existing storage-IPC pattern but was NOT run live in a packaged build this session** — only the dev path was exercised. Sanity-check it in an actual Electron run.
- **Browser dev (`npm run dev`):** Vite `server.proxy` forwards `/archidekt/*` → `https://archidekt.com` server-side (see `vite.config.ts`). **Changing this proxy requires a dev-server restart** — HMR won't pick up `vite.config.ts` changes.
- A plain hosted browser build (neither) can't reach it — surfaced as "Link import only works in the desktop app."

### Export → Tabletop Simulator (TTS) compatibility

**Multi-format export, `engine/deckExport.ts`.** `ExportDeckModal.tsx` has a Format dropdown
(`EXPORT_FORMATS`) driving `formatDeckExport(format, cards, cardsById)`:

- **`archidekt`** (`formatArchidektExport`) — Archidekt's own plain-text export
  (`1x Name (set) 123 [Tag]`), round-trips with `parseArchidektExport` in `deckImport.ts`. Emits
  **exactly one tag per line**, never comma-joined — regression-tested in `deckExport.test.ts`
  (asserts no line's tag contains a comma). Priority when a card has multiple reasons to tag:
  Commander → Maybeboard → its own category. Includes sideboard cards (tagged Maybeboard).
- **`dec`** (`formatDecExport`) — `1 [SET] Name`, mainboard only.
- **`arena`** (`formatArenaExport`) — MTG Arena's `.txt` export, `1 Name (SET) 123`, mainboard only.
- **`mtgo`** (`formatMtgoExport`) — MTGO's simple `.txt`, `1 Name`, mainboard only.

All three non-Archidekt formats **omit sideboard cards entirely** rather than inventing tag syntax
those formats don't have — same practical outcome as Maybeboard (they don't end up on the table).

**Why this exists — real debugging trail, useful if TTS export breaks again:**
1. First hypothesis (wrong data, right instinct): our Archidekt-format export emitted comma-joined
   multi-tags (`[Draw,Maybeboard]`); confirmed via the "MTG Deck Loader / Importer" TTS mod's own
   docs that its grammar is a single `[<category>]` tag. Fixed `buildTag` to emit one tag — real
   bug, worth keeping, but turned out **not to be what the user's actual table uses**.
2. User clarified their table is **"MTG 4 player table - scripted"**, which bundles a *different*
   importer — **rikrassen's "MTG Deck/Draft/Cube Importer"** (one of three importer options there).
   Its docs aren't public, so a second, broader hypothesis (Scryfall blocking card-data requests
   from TTS generally) was researched and looked plausible from search results, but was never
   confirmed against this specific importer.
3. **Ground truth came from the importer's own in-app help screen** (a screenshot, not a web
   search): it accepts exactly three formats — `.dec` (`1 [9ED] Storm Crow`), MTG Arena `.txt`
   (`1 Storm Crow (9ED) 100`), and MTGO `.txt`/simple (`1 Storm Crow`) — and **does not mention
   Archidekt's bracket-category syntax at all**. That's the actual root cause: this importer was
   never going to accept our (or even Archidekt's own) `[Tag]` format, regardless of single vs.
   multi-tag.

**Lesson for next time a TTS import error shows up:** don't assume which importer/mod is in play,
and don't trust web-search paraphrases of a mod's format over the mod's own in-app help text if the
user can screenshot it — that's what actually resolved this. If it happens again, ask which
Workshop mod/importer specifically, and whether it has its own help/format screen, before touching
`deckExport.ts`.
